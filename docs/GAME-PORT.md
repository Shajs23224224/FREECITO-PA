# Contrato GamePort — integración permitida

La aplicación no está conectada a un videojuego concreto. Para integrar un título, su propietario debe proporcionar una API oficialmente permitida para automatización, observación y comandos en una partida privada o entorno expresamente autorizado. No usar inyección de entradas, accesibilidad para jugar, lectura de memoria, ingeniería de protocolos, elusión de protecciones, automatización de partidas públicas competitivas ni compras con dinero real.

AuthorizedGameAdapter define title, memoryScope (juego y versión), launch, captureScopeConfirmed y commandPort opcional. GamePort.scope debe coincidir exactamente con memoryScope. authorized debe consultar permiso activo. observe devuelve GameState de datos visibles/autorizados: secuencia creciente, tiempo monotónico compatible con elapsedRealtimeNanos, inventario, objetivos de cantidad aprobados y hasta 32 ofertas vigentes. No se incluyen identificadores de cuentas. Las ofertas deben describir recursos internos y ser virtualOnly únicamente cuando no existe pago real, moneda comprada ni consecuencia económica externa.

submit debe validar de forma atómica la sesión, permiso, secuencia, caducidad y oferta; false significa rechazo definitivo sin ejecución. No debe bloquear. Un recibo posterior debe referirse al mismo commandId y confirmarse mediante el estado actualizado. stop revoca permisos y cancela comandos pendientes; debe ser idempotente. Una excepción o resultado incierto bloquea nuevas órdenes durante la sesión. La validación del adaptador sigue siendo responsabilidad del integrador: la interfaz no prueba por sí sola la autorización.

Familias inicialmente habilitadas: INSPECT, EXPLORE, COLLECT, EXCHANGE_VIRTUAL. EQUIP y USE están tipadas, pero no se eligen hasta validar necesidad/efecto específico. No hay acciones de combate implementadas en esta fase. No se incluyen ejemplos de implementación de juegos ni endpoints inventados. No se utiliza un simulador.
